运维故障排查实战手册：那些年我们踩过的坑和解法

发表于2026-05-23|更新于2026-05-23|运维
|浏览量:

前言：故障排查是运维的”真功夫”

如果你问我，运维工程师最核心的能力是什么？不是会搭 K8s 集群，不是能写 Ansible Playbook，甚至不是精通 Docker——而是故障排查。

因为生产环境永远会出问题。不管你的架构设计得多完美、监控做得多全面，故障总会以你意想不到的方式出现。而当你凌晨三点被电话叫醒，面对一个正在宕机的生产系统时，你需要的不是翻文档，而是肌肉记忆般的排查思路。

这篇文章整理了我在实际工作中遇到的经典故障案例和排查方法，分为系统层、网络层、应用层、数据库层、容器与 K8s 层五个维度。每个案例都包含现象、排查过程、根因分析、解决方案四个部分。

建议你先通读一遍建立整体认知，然后把排查思路内化为自己的方法论。真正遇到故障时，你会感谢现在的自己。

一、故障排查的通用方法论

在深入具体案例之前，先建立一个通用的排查框架。我把它总结为 “五步排查法”：

第一步：确认现象

不要急着动手。 先搞清楚到底发生了什么：

  • 是所有用户都受影响，还是部分用户？
  • 是完全不可用，还是响应变慢？
  • 是突然出现，还是逐渐恶化？
  • 最近有没有做过变更（发布、配置修改、扩容）？

经验之谈：超过 60% 的生产故障都与最近的变更有关。每次排查前先问一句”最近改了什么”，往往能直接定位问题。

第二步：定位层次

按照 OSI 七层模型或简化版的四层来逐层排查：

从外向内、从上到下，逐层缩小范围。不要一上来就去看应用日志——如果问题出在 DNS 层，你看一天日志也找不到原因。

第三步：收集证据

在定位到具体层次后，收集相关证据：

  • 系统指标：top、htop、vmstat、iostat、free -h、df -h
  • 网络状态：ss -tlnp、netstat、tcpdump、curl -v
  • 应用日志：tail -f、grep、journalctl
  • 监控数据：Prometheus/Grafana 的趋势图

第四步：分析根因

基于证据进行推理，找到根本原因而非表面现象。

比如：应用日志显示”Connection refused”，这不是根因。你需要继续追问：为什么 refused？是服务没启动？端口被占用？防火墙拦截？还是连接数达到上限？

多问几个”为什么”，直到找到可以直接修复的那个点。

第五步：修复并复盘

修复后不是结束，而是开始。你需要：

  • 写故障报告（什么时候发生、影响范围、根因、修复方案）
  • 思考如何避免同类故障再次发生
  • 是否需要补充监控告警
  • 是否需要改进架构或流程

二、系统层故障排查

案例 1：CPU 飙到 100%，服务响应极慢

现象： 告警系统显示某台服务器 CPU 使用率持续 99%，用户反馈页面加载超时。

排查过程：

发现 Java 进程占了 98.7% CPU。

线程 12389 占了绝大部分 CPU。

根因分析： 一个数据批处理任务在处理超大文件时进入了死循环——processLargeFile 方法没有正确设置退出条件，当文件行数超过阈值时，while 循环永远不会结束。

解决方案：

举一反三： CPU 飙高的常见原因还包括：

  • 死循环 / 无限递归：代码逻辑 bug
  • GC 风暴：频繁 Full GC，JVM 把大量时间花在垃圾回收上
  • 正则表达式回溯：复杂正则在特定输入下的灾难性回溯
  • 线程竞争：大量线程争抢同一把锁

案例 2：磁盘空间告警，但 du 查不到大文件

现象： 监控告警磁盘使用率 95%，但 du -sh /* 统计下来只用了 40%。

排查过程：

根因分析： 应用日志文件 /var/log/app.log 被运维人员用 rm 命令删除了，但是 Java 进程仍然持有该文件的文件描述符。在 Linux 中，只有当一个文件的所有硬链接都被删除且所有文件描述符都被关闭时，磁盘空间才会真正释放。所以虽然 rm 了，但空间并没有还回来。

现象： 服务突然不可用，dmesg 中出现 OOM 相关日志。

三、网络层故障排查

案例 4：服务间歇性超时，ping 正常但 curl 偶尔失败

现象： 用户反馈接口偶尔超时（约 5-10 秒），但服务器 ping 延迟正常（<1ms），监控显示 CPU 和内存都正常。

排查过程：

抓包发现超时请求中，TCP 三次握手正常完成，但之后出现了多次重传，直到 5 秒后连接才真正建立。

根因分析： iptables 的连接跟踪表（conntrack）满了。当连接数超过 nf_conntrack_max 时，新连接的数据包会被直接丢弃，导致 TCP 重传，表现为间歇性超时。

案例 5：Nginx 502 Bad Gateway

现象： 访问网站返回 502 Bad Gateway。

排查过程：

根因分析： 后端 Java 应用因内存不足崩溃，Nginx 无法连接到上游服务，返回 502。

七、故障预防：比排查更重要的是不发生故障

排查能力再强，也只是事后补救。真正优秀的运维工程师，追求的是让故障不发生。以下是几条经过实践验证的预防策略：

1. 变更管理：所有故障的万恶之源

前面说过，超过 60% 的故障与变更有关。建立严格的变更管理流程：

  • 所有变更必须经过 Code Review
  • 生产变更必须有回滚方案
  • 大变更选择低峰期执行
  • 变更后观察监控至少 15 分钟

2. 监控告警：在用户发现之前你先发现

一个完善的监控体系应该覆盖四个层次：

  • 基础监控：CPU、内存、磁盘、网络
  • 中间件监控：MySQL 连接数/慢查询、Redis 命中率/内存、Nginx QPS/错误率
  • 应用监控：接口响应时间、错误率、QPS
  • 业务监控：订单量、注册量、支付成功率

告警配置的关键原则：宁可漏报也不要误报。过多的误报会导致”告警疲劳”，真正的故障告警反而被忽略。

3. 混沌工程：主动制造故障

Netflix 的 Chaos Monkey 理念——在生产环境中随机杀掉服务实例，验证系统的容错能力。你可以在测试环境实践：

4. 文档和 Runbook

为每一种常见故障编写 Runbook（运维手册），包含：

  • 故障现象描述
  • 排查步骤（按顺序）
  • 解决方案
  • 升级路径（自己搞不定时找谁）
  • 事后复盘模板

当凌晨三点被叫醒时，一份清晰的 Runbook 能让你在 10 分钟内恢复服务，而不是花 2 小时从零开始排查。

八、排查工具箱：你的瑞士军刀

最后整理一份运维排查必备的工具清单：

系统层

工具 用途 快速上手
htop 交互式进程/资源监控 直接运行，按 F6 排序
iostat -x 1 磁盘 I/O 监控 关注 %util 和 await
vmstat 1 虚拟内存统计 关注 si/so（swap）和 r/b（运行/阻塞进程）
strace -p PID 跟踪系统调用 排查进程卡在哪个系统调用
lsof -p PID 查看进程打开的文件 排查文件描述符问题

网络层

工具 用途 快速上手
ss -tlnp 查看监听端口 替代 netstat，更快
tcpdump -i eth0 port 80 抓包分析 配合 Wireshark 分析
curl -v URL 详细 HTTP 请求 查看完整的请求/响应头
mtr HOST 路由追踪 比 traceroute 更直观
dig DOMAIN DNS 查询 排查 DNS 解析问题

应用层

工具 用途 快速上手
strace -e trace=network 跟踪网络调用 排查连接问题
arthas Java 在线诊断 阿里开源，功能强大
py-spy Python 性能分析 不需要修改代码
httping HTTP 层的 ping 测试 Web 服务可用性

Kubernetes 专用

工具 用途 快速上手
k9s K8s 交互式终端 比 kubectl 更直观
stern POD 多容器日志聚合 一次看所有容器日志
kubectl-debug 在 Pod 中启动调试容器 排查不含 shell 的容器
lens K8s 桌面 GUI 可视化管理集群

结语

运维故障排查没有捷径，只有经验的积累。每一次故障都是一次学习的机会——如果你能从每次故障中提取出可复用的知识，建立自己的”故障案例库”，那么随着时间推移，你的排查速度会越来越快，遇到的”未知故障”也会越来越少。

记住这三句话：

  1. 不要猜测，用数据说话。 每一次排查都应该基于监控数据、日志和系统指标，而不是”我觉得可能是……”。
  2. 先止血，再治病。 生产环境优先恢复服务（重启、回滚、切流量），事后再排查根因。
  3. 每一次故障都是财富。 把踩过的坑记录下来，分享给团队，这是运维工程师最有价值的知识资产。

希望这篇文章能成为你排查故障时的案头手册。下次遇到问题时，翻出来对照着一步步排查，你会发现——原来那些看似复杂的故障，背后都有清晰的逻辑链条。
